# simplify-code — 代码精炼

> Compound Engineering 核心理念：让每一单位工程工作使后续工作更简单。精炼（simplify）是
> 「写完就收敛」的一环——新代码的复杂度不在审查阶段才被发现，而在提交审查前先自我精炼一遍。

## 适用场景与范围

| 触发点 | 范围信源 |
|---|---|
| 完整流程 P2 完成、P3 审查前（建议但非强制，由主 Agent 或开发 Agent 判断） | 本任务 dev-pass `allowedPaths`（task-dag.json `files[]`） |
| quick 模式修改完成、done 前 | `quick-task.json` 的 `files[]` |

**只在范围内精炼**：范围外的文件一律不碰（dev-pass 限域会强制拦截越界编辑）。

## 精炼原则（全部是「不改行为语义」的收敛）

1. **删无用代码**：未使用的变量/导入/分支/函数；为「将来可能用到」而写的死路径。
2. **删无用测试**：与被改行为无关的过时断言；因需求变化而失效的用例（保留仍有效的回归）。
3. **收敛注释**：删除复述代码的注释；保留「为什么这么做」的注释；TODO 必须带上下文与责任人。
4. **降复杂度**：合并重复逻辑、收窄过宽的接口、删除过度防御（无法发生分支）。
5. **不做的事**：不重命名公共 API、不改函数签名、不移动文件、不「顺手」重构相邻代码、
   不引入新抽象——这些都属于行为/接口变更，超出精炼边界。

## 执行步骤

1. 读取范围（dev-pass / quick-task.json），`git diff` 获取本次变更。
2. 逐文件检查上述五类问题，编辑收敛。
3. 精炼后必须重跑与改动相关的既有自测/构建（quick 模式下即 evidence 的复验）。
4. 留痕：
   - 完整流程：`development-notes/simplify-<taskId>.md`（若 story 无 taskId 维度则用 storyId），
     记录精炼点与复验结果，随 P2 交付说明一起进入审查。
   - quick 模式：把精炼说明追加进 `quick-task.json` 的 `evidence[]`，不单独落盘。

## 边界与安全

- 精炼后的代码照常走 P3 审查 / quick 的定向自测，精炼不代替审查。
- 精炼造成的失败按普通实现返修处理（fix-loop / quick 重做），不因「只是清理」而放松门槛。
- 大量删除（>50 行）时在留痕中说明删除理由，供审查师核对。
