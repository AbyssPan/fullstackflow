# 根因调查与修复验证

## 输入与权限

读取错误现象、复现步骤、AC、相关日志与最近变更；Bug 报告中的路径是候选位置，不能直接认定根因。
遵守 [影响面分析](../harness-conductor/references/代码检索规范.md) 与 [验证与交付](../harness-conductor/references/verification.md)。
本技能不创建另一套状态机。Phase 0 只调查并输出事实；Phase 2 才在 dev-pass 范围内修复；Phase 4 只验证和交接。

## 调查过程

1. **明确现象**：记录预期/实际、版本、环境、触发输入和发生频率。读取完整相关错误栈。无法复现时保留证据和未知条件，不编造稳定复现。
2. **缩小边界**：查最近改动和同仓正常实现；沿入口、请求、业务层、存储/缓存逐段对照输入输出，定位最早出现偏差的位置。日志只采集必要且脱敏的字段；仅在允许修改源码的阶段添加临时诊断。
3. **验证假设**：写明「怀疑 X，因为证据 Y；若成立，应观测 Z」，一次只改变一个相关变量。反证出现时放弃或修正假设，不叠加猜测性补丁。
4. **确认范围**：用源码确认调用方、共享状态、间接入口与回归路径。原因在上游时指出原报告为何只定位到表象；超出任务写入范围先交规划/编排调整授权范围，不自行扩权。
5. **修复与验证**：在允许的阶段实现最小根因修复，复测原始症状与受影响路径。能稳定复现的逻辑缺陷优先形成回归用例；确认用例在修复前因同一原因失败、修复后通过。需要还原对照时使用隔离临时副本，不覆盖用户工作区改动。

## 停止盲试

一次实验失败先整理新增事实，再选择下一假设。反复失败、每次修复引出不同共享状态问题或必须大范围改架构时，汇报已排除项和阻塞证据。
工作流重试次数沿用现有 fix-loop 预算，不能在技能内另开无限重试；预算耗尽交编排器处理。
环境、外部服务或偶发时序问题可形成「根因未确认」结论，附下一步观测方案；不能仅因已加重试就宣称根因已解决。

## 输出到既有产物

Phase 0 的 Bug 分析报告记录事实、证据、责任边界和未确认项，不提前替开发决定改法。
Phase 2 在 development-notes/<taskId>.md 记录：原现象 → 根因证据 → 实际修改 → 影响范围 → 验证结果/限制。
Phase 4 将复现证据与失败 AC 写入测试报告，交开发修复，不直接修改业务源码。
