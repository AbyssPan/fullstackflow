# 设计还原与交互验证

## 从设计数据到组件

使用任务绑定的精确 figmaRefs 获取布局上下文与截图。截图辅助视觉核对，尺寸、变量、状态优先取设计数据；缺失信息按项目规范补位，涉及产品行为的分歧记录待确认项。

先检索既有 Token、组件、主题和图标资源，再提取实际新增值。共享 Token 放入项目现有全局入口，组件只消费；不要把 :root 放进 scoped 样式，也不要为本次页面复制完整 Token 表。已有主题覆盖和局部变量允许按项目约定存在，不把所有同名变量判成重复缺陷。

设计中的重复块映射到现有组件；Auto Layout 按实际布局用 flex/grid，浮层才考虑定位。组件库默认样式与设计不一致时只覆盖差异属性，同时保留键盘、焦点、禁用和加载行为。
资源优先使用设计交付或项目已有资源；无法获取时明确缺口，不能用不相干的图片冒充完成还原。

## 设计未画出的状态

- 空态、失败、禁用、超长文本、图片失败、窄屏溢出仍须有可用行为；优先使用已确认需求和项目既有模式。
- 不凭单张桌面稿杜撰另一套移动产品，但必须检查目标视口范围。无法确定交互或布局取舍时，集中询问真正影响验收的点。
- 语义化控件、可访问名称、键盘操作、弹窗焦点进入/返回不能因设计稿未标注而省略；设计冲突需给出具体影响与最小调整建议。

## 验证清单

固定视口、字体、数据和交互状态后对照设计截图，记录布局、间距、颜色、排版、文案、资源和状态偏差。
检查业务路由或实际父组件能否到达目标页面，包含动态导入、自动注册和间接使用；只搜索直接 import 不足以断言组件未集成。
视觉回归采用项目已有基线与阈值，动态区域按业务意义处理。基线更新必须说明对应的预期视觉变化，不能为消除差异直接重录。
结论与截图/路由/状态写入现有交付说明；视觉吻合不能代替交互验收。
