# 前端规范解析与执行

## 规范解析

1. 读取任务 AC、已确认决策和相关知识库章节；缺库时直接查仓库，不重复初始化。
2. 检查目标模块的 package.json、锁文件、框架/构建版本、类型与 lint 配置、路由、请求封装、状态库、UI 库及相邻实现。单仓多应用分别识别，不以文件扩展名认定运行环境（Node.js 的 TS 不是浏览器代码）。
3. 优先级：用户要求与 AC → 有效的项目知识库/仓库明确规范 → 适用的内置审查规则 → 相邻代码稳定约定 → 本技能默认基线。项目风格不能降低安全与数据正确性要求；过期规范与当前依赖冲突时记录证据、保留兼容实现。
4. 在现有 development-notes 或审查 notes 中简记「项目规则、沿用约定、默认补位、冲突/未知」。只加载命中的参考，不批量整改旧代码。

## 读取路径

- 所有前端编码与审查：读 [工程规则](references/engineering.md)，按 JS/TS、框架版本和运行端筛选。
- 有设计稿、样式或交互变更：读 [设计与交互](references/design.md)。Figma 节点仍由 figma-to-component-map 绑定，本技能不另建流程。
- 共享模块或跨页面变更：遵守 [影响面分析](../harness-conductor/references/代码检索规范.md)。
- 完工或交接：遵守 [验证与交付](../harness-conductor/references/verification.md)。

## 编码与审查衔接

开发前声明本次组件边界、状态归属和接口数据流，简单修改可合并为一句话；使用既有组件和封装完成最小变更。
开发后检查真实业务入口、需求要求的数据消费、状态分支与生命周期清理。审查时按同一套适用规范查证，不把模板偏好当缺陷。

沿用项目检查命令，区分 lint、类型检查和构建的结论。跨框架写法、样式预处理或构建配置变更应执行相应检查；无法执行时交接限制，不能用 lint 通过代替构建成功。
工作流内只在 Phase 2 且 dev-pass 范围内修改源码；修复任务不能借规范补齐扩大范围。
