# 验证、授权与交付约定

## 证据与结论

每项完成声明必须对应实际证据：代码已写入看 diff；lint/类型/构建各看对应命令；Bug 修复看原症状复测；需求满足逐项对照 AC。
记录版本（HEAD 加相关工作区变更）、范围、环境、命令/操作、退出码或断言结果、未覆盖项。同版本同范围且环境未变化的证据可以复用；相关代码、配置、依赖或环境变化后重新验证受影响部分，不按消息轮次机械重跑。
子 Agent 自述、文件存在、Schema 合法只能证明对应事实，不能独立证明业务正确。主控核对产物与证据，不凭“已完成”推进。

| 实际情况 | 可报告结论 |
|---|---|
| 代码修改完成，未运行 | 已实现，运行行为待验证 |
| 部分检查通过 | 列明已通过范围和剩余缺口 |
| 运行结果不符合预期 | 验证失败，附预期/实际和证据 |
| 环境或权限阻塞 | 无法验证，说明缺少条件与可执行下一步 |

只读审查需检查实际命令定义：npm run lint 可能包含 --fix，tsc 可能生成增量缓存；不要仅凭名称判断无写入。只执行与角色权限相符的检查。

## 阶段分工与证据复用

| 阶段 | 负责的结论 | 避免重复的方式 |
|---|---|---|
| P0 需求 / P1 规划 | 做什么 / 如何拆解与限定范围 | 复用已确认需求；符合现有轻量条件时一次准备两阶段产物，仍分别过门控 |
| P2 开发 | 实现与定向自测 | 本任务 AC、Bug 复现和受影响回归优先；不另做完整独立审核 |
| P3 审查 | 变更逻辑、风险与跨文件影响 | 核对已有检查证据，一轮审查；修复后仅补审变化及影响范围 |
| P4 功能测试 | 全部 AC 的运行行为和覆盖缺口 | 核验 P2/P3 运行证据，补测未覆盖或失效行为，不再全量审代码 |
| P5 提交 / P6 合入核验 | 提交内容 / 实际合入版本 | P5 维护知识，P6 只核验实际合入提交，不重复写知识正文 |
| P7 发布 | 构建部署与交付状态 | 引用前序证据；发布构建针对最终环境，不能用本地检查替代 |

P4 复用前序自测必须由测试工程师核对原始日志、响应或截图与断言，不仅采信开发者摘要。逐条核对 AC 的 Given/When/Then、相关代码与工作区内容、配置/依赖、运行环境和数据前提；全部一致且证据可读取才可复用。在 acceptance-verification 的 notes 写来源路径、版本、覆盖断言及复用依据，evidenceType 保留真实执行类型，不能伪装成本阶段新执行。
前序只检查返回码，不能证明落库或 UI 状态；Mock、静态阅读、lint 和构建均不能替代真实 UI/API 行为。无法证明一致性就重跑受影响项，环境不具备则 unverifiable。高风险变更补充独立的关键失败/权限/数据一致性路径验证；用户明确要求独立重跑时执行。最终仍逐条覆盖所有 AC。
同一行为选能证明它的最低必要测试层次；跨端契约、事务或用户完整流程仍需相应集成/E2E，不机械要求单元、接口、E2E 三层各跑一遍。必过门控、Git hook、CI 和实际合入版本检查照常执行，不能因文字说明中“已有证据”跳过；本约定不引入自动缓存或绕过门控。

## 授权与流程边界

沿用当前会话明确的范围和授权，日常定位、实现、自测不增加重复确认点。外部发布、消息发送、环境变更等按当前授权执行，缺失授权时展示具体对象与操作再询问。
独立功能测试遵守 verificationMode；本文件不覆盖用户跳过选择。技能不能手改 e2e-state/dev-pass 或自行推进阶段。
文档来源、常规实现细节可由仓库事实确定时先查证；只有影响产品行为、范围或无法从事实确定的决策才交用户裁决。
